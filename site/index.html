capsule

Local execution for agent-generated code.

Capsule is a local-first project under development for running JavaScript and TypeScript jobs proposed by AI agents. Each job is intended to require an exact plan, human approval, and explicit resource and capability limits before it runs.

What Capsule is

Capsule is intended to provide a small local execution service for bounded, one-shot jobs—not a general computer. The public unit is a job with source, input, allowed capabilities, exact limits, and a declared result. Containers, virtual machines, and language runtimes remain implementation details.

The first planned executable slice is dependency-free TypeScript with inline JSON input and bounded JSON output. Network access, subprocesses, inherited environment variables, native add-ons, foreign-function interfaces (FFI), package installation, arbitrary images, and host paths are outside that slice.

What Capsule is not

Capsule is not a shell, development environment, general-purpose virtual machine, or hosted sandbox. It does not determine whether generated code is correct, and it cannot prevent approved output, metadata, or timing from revealing approved input.

How the intended system works

The design separates planning, human approval, and execution so the agent-facing service does not control all three.

Daemon
Agent-facing planning service
Validates proposals, resolves trusted policy, and constructs exact plans. It is not allowed to approve a plan or launch a guest.
Approval Broker
Trusted native approval interface
Fetches registered typed plan data, presents it to the user, requires fresh user presence, and signs one-use approval.
Execution Supervisor
Trusted execution authority
Registers exact plan bytes, enforces hard safety rules, creates one approved attempt, and owns backend cleanup and enforcement evidence.
Isolation backend
External host boundary
Contains the guest outside the language runtime. Runtime permission systems are only supplemental hardening.

What is implemented today

Capsule is a buildable scaffold, not a usable sandbox. The repository contains strict unwired proposal, plan, and registration conformance code; deterministic TypeScript construction of the minimum plan; and Go registration-state handling.

Current lifecycle work
Durable no-guest fake lifecycle
An unwired Go path registers exact bytes, consumes a candidate approval into one attempt, and records fake lifecycle intents, effects, cleanup, recovery, and capacity state in one fixed local snapshot. The fake backend is hard-coded to create no guest.
Not yet connected
No product execution path
The internal mechanics have no product consumer. Authenticated local IPC, production Broker signing and UI, content handling, composed evidence, an admitted runtime and backend, and a signed installed topology remain incomplete or under investigation.

Security requirements

These are requirements for the intended security model, not claims about the current implementation.

Separated authority
Planning, approval, and execution have different owners
Registered plans only
Execution accepts a Supervisor-issued plan ID, never replacement plan bytes
One-use approval
Human approval is bound to one exact plan and at most one execution attempt
Immutable input
File inputs become content-addressed snapshots instead of live host paths
External isolation
A separate sandbox or virtual machine must contain hostile guest code
